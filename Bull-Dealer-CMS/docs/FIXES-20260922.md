# Version 1.0.1 — local backend repair (2026-09-22)

## Evidence and cause

The input ZIP's root .env had Docker MYSQL_* and ADMIN_* settings but no DATABASE_URL. Neither the API nor migration/seed commands loaded .env. The local startup script depended on .local/runtime.json and a portable MySQL directory that were absent from the ZIP. npm run dev did not migrate or seed a database. The original repository constructed a lazy MySQL pool without checking the schema; health checked only SELECT 1.

Reproduced against an isolated empty MySQL database using the original API: health HTTP 200, admin login HTTP 500, dealer site API HTTP 503. Login queried missing cms_users; site queried missing dealer tables. A pre-username schema can also fail login with ER_BAD_FIELD_ERROR. An unreachable database can present a Vite proxy HTTP 500 when the API never starts.

These defects reproduce the reported symptoms. The user's original running database and server error log were not available for inspection, so its exact MySQL error is not claimed. The installed MySQL80 service and its data were not modified; tests used a separate MySQL process and data directory on port 13307.

## Changes

- Shared root .env loading for API, migrations, bootstrap and credential commands. Explicit process environment takes precedence.
- Documented DATABASE_URL and port 3000; removed private-machine dependencies from local startup instructions/script.
- Added db:setup (build, migrate, seed). Existing accounts/publications are preserved; password reset remains explicit.
- API checks required schema and an active super administrator before accepting requests; failures name the database error code and repair commands without exposing credentials.
- Reject malformed password hashes without throwing; preserve significant password whitespace.
- Docker API startup now runs the repeatable migration before bootstrap, including existing volumes.
- Portable integration suite accepts TEST_DATABASE_URL instead of private .local/runtime.json.
- Added local proxy/auth/hostname smoke test and password regressions.
- No dealer/admin UI source, CSS, images or branding changed. Vite proxies and tenant resolution were already correct and remain unchanged. No demo fallback or catch-all tenant fallback added. Same-origin proxies make a CORS change unnecessary.

## Verification performed

Windows, Node 24.19.0, MySQL Community 8.0.46 isolated instance:

- Clean npm ci; TypeScript checks; 10/10 unit tests; all production builds passed.
- Fresh db:setup creates schema, first admin and published Tara content. Repeat setup preserved the changed administrator password and the original publication.
- 20/20 integration checks passed across 130 disposable dealers: authentication, publishing scopes, drafts, precedence, tenant isolation, contact persistence, media, onboarding and session revocation. See TEST-RESULTS.json generated by this run.
- API health 200 in mysql mode; dealer /api/site 200 through Vite port 5173.
- Username login through admin Vite port 5174 returns 201 and a usable session; wrong password 401; protected dashboard 200; logout revokes session.
- Host-header tests: localhost, 127.0.0.1, [::1], mixed-case production hostname with port resolve correctly; unknown hostname returns 404.
- Missing schema, wrong database password and missing username column all fail startup with an actionable error and exit code 1. Migration restored username on an older schema without removing the dealer.
- Browser: dealer homepage renders Tara/BULL content; /admin/login authenticates and shows dashboard, active Tara dealer and publication.
- UI/assets compared byte-for-byte with input ZIP (frontend source, CSS and public assets unchanged).

Sandbox restrictions initially blocked Windows esbuild/tsx system access; rerunning the same commands outside that sandbox passed. This was a test-environment constraint, not a project change.

Not executed: Docker containers, MySQL 8.4 specifically, R2 uploads. Existing user databases require their real connection details and migrations; no database or credential file is bundled.

Additional port verification: existing user Vite servers occupied 5173/5174. Their proxies were exercised against the repaired API, and the packaged frontends were then independently launched on 15173/15174. Browser tests on those spare ports also passed (dealer rendering and admin dashboard after sign-in). The user's existing frontend processes were left untouched; all temporary repair-test services were stopped after verification.
